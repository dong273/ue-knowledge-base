# UE 5.7 GAS API Migration Guide

## Background

This project ([REDACTED]) runs on UE 5.7. Several GAS-related APIs changed between UE 5.3-5.5 and 5.7. Code generated by AI models trained on older UE5 documentation will fail to compile. This reference documents the exact fixes.

---

## 1. `ActivateAbility` / `EndAbility` — Parameter Type Change

**Error:** `error C3668: 'ActivateAbility': method with override specifier did not override any base class method`

**Cause:** The third parameter changed from `FGameplayAbilitySpec` to `FGameplayAbilityActivationInfo`.

**Affects:** Both `.h` declaration and `.cpp` definition, in both `ActivateAbility` and `EndAbility` (4 sites total per ability class).

`cpp
// ❌ WRONG (UE 5.3-5.5)
virtual void ActivateAbility(
    const FGameplayAbilitySpecHandle Handle,
    const FGameplayAbilityActorInfo* ActorInfo,
    const FGameplayAbilitySpec ActivationInfo,         // ← wrong
    const FGameplayEventData* TriggerEventData) override;

// ✅ CORRECT (UE 5.7)
virtual void ActivateAbility(
    const FGameplayAbilitySpecHandle Handle,
    const FGameplayAbilityActorInfo* ActorInfo,
    const FGameplayAbilityActivationInfo ActivationInfo, // ← correct
    const FGameplayEventData* TriggerEventData) override;
`

Same fix applies to `EndAbility` — same third parameter type.

## 2. `GetFloatAttributeFromAbilitySystem` — Removed

**Error:** `error C3861: 'GetFloatAttributeFromAbilitySystem': identifier not found`

**Cause:** This utility function was removed from `UAbilitySystemBlueprintLibrary` in UE 5.7.

`cpp
// ❌ WRONG
float Stamina = UAbilitySystemBlueprintLibrary::GetFloatAttributeFromAbilitySystem(
    ASC,
    UBAttributeSet_Stamina::StaticClass()->GetDefaultObject<>()->GetStaminaAttribute(),
    -1.0f  // fallback value
);

// ✅ CORRECT
float Stamina = ASC->GetNumericAttribute(
    UBAttributeSet_Stamina::StaticClass()->GetDefaultObject<UBAttributeSet_Stamina>()
        ->GetStaminaAttribute()
);
`

**Note:** `GetNumericAttribute()` has no fallback/sentinel value. If the attribute isn't registered on the ASC, behavior is undefined. Always ensure the `UAttributeSet` is created and registered before calling this.

**Also remove:** `#include "AbilitySystemBlueprintLibrary.h"` is no longer needed if this was the only function used from it.

## 3. `GrantedTags` — Removed from UGameplayEffect Constructor

**Error:** `error C2065: 'GrantedTags': undeclared identifier`

**Cause:** In UE 5.7, `UGameplayEffect::GrantedTags` (a `FInheritedTagContainer`) was removed from the class definition. Tags that a GE grants must now be set on the `FGameplayEffectSpec` at application time instead.

`cpp
// ❌ WRONG — in UGameplayEffect subclass constructor
UGE_Exhaustion::UGE_Exhaustion()
{
    DurationPolicy = EGameplayEffectDurationType::HasDuration;
    DurationMagnitude = FScalableFloat(1.5f);
    GrantedTags.AddTag(FGameplayTag::RequestGameplayTag("State.Exhausted")); // C2065
}

// ✅ CORRECT — keep GE simple, set tags at application point
// GE_Exhaustion.cpp: no GrantedTags line
// GA_Sprint::EndAbility (or wherever the GE is applied):
FGameplayEffectSpecHandle Spec = ASC->MakeOutgoingSpec(UGE_Exhaustion::StaticClass(), 1.0f, Ctx);
if (Spec.IsValid())
{
    Spec.Data->DynamicGrantedTags.AddTag(FGameplayTag::RequestGameplayTag("State.Exhausted"));
    ASC->ApplyGameplayEffectSpecToSelf(*Spec.Data.Get());
}
`

**Pattern:** For any GE that needs to grant tags:
1. Remove the `GrantedTags.AddTag(...)` line from the constructor
2. Find every call site where the GE is applied via `MakeOutgoingSpec` + `ApplyGameplayEffectSpecToSelf`
3. Add `Spec.Data->DynamicGrantedTags.AddTag(...)` before applying

## 4. `AddLambda` on Dynamic Multicast Delegates — Not Supported

**Error:** `error C2039: 'AddLambda': not a member of 'FInputReleaseDelegate'`

**Cause:** Delegates declared with `DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam` (like `FInputReleaseDelegate`) do not support `AddLambda()` or `AddUObject()` in UE 5.7. They only support `AddDynamic()` which requires the handler to be a `UFUNCTION()`.

`cpp
// ❌ WRONG
UAbilityTask_WaitInputRelease* Task = UAbilityTask_WaitInputRelease::WaitInputRelease(this);
if (Task)
{
    Task->OnRelease.AddLambda([this](float TimeHeld) {
        OnInputReleased(TimeHeld);
    });
    Task->ReadyForActivation();
}

// ✅ CORRECT
// In header, mark the handler as UFUNCTION():
//    UFUNCTION()
//    void OnInputReleased(float TimeHeld);

UAbilityTask_WaitInputRelease* Task = UAbilityTask_WaitInputRelease::WaitInputRelease(this);
if (Task)
{
    Task->OnRelease.AddDynamic(this, &UGA_Sprint::OnInputReleased);
    Task->ReadyForActivation();
}
`

**Scope:** This applies to ALL dynamic multicast delegates, not just ability task delegates. Common UE types affected:
- `FInputReleaseDelegate` (ability tasks)
- `FOnGameplayAttributeValueChange` (attribute set)
- Any `DECLARE_DYNAMIC_MULTICAST_DELEGATE_*` in your own code

## 5. `PrivateIncludePaths` — Deprecated in Build.cs

**Error:** `fatal error C1083: Cannot open include file` for files in sibling subdirectories.

**Cause:** `PrivateIncludePaths.Add()` and `PublicIncludePaths.Add()` in ModuleRules are deprecated in UE 5.7+ and do not add include directories.

**Fix:** Use relative `#include` paths from the source file's own directory:

| Source file location | Target header | Include syntax |
|---------------------|---------------|----------------|
| `Abilities/GA_Sprint.cpp` | `Attributes/BAttributeSet_Stamina.h` | `#include "../Attributes/BAttributeSet_Stamina.h"` |
| `Effects/GE_SprintSpeedBoost.cpp` | `Attributes/BAttributeSet_Stamina.h` | `#include "../Attributes/BAttributeSet_Stamina.h"` |
| `Source/[REDACTED]/` (root) | `Attributes/BAttributeSet_Stamina.h` | `#include "Attributes/BAttributeSet_Stamina.h"` |
| `Abilities/GA_Sprint.cpp` | `Effects/GE_SprintSpeedBoost.h` | `#include "../Effects/GE_SprintSpeedBoost.h"` |

**Rule:** `#include "..."` first searches the source file's own directory, then falls back to configured include paths. For flat UE5 modules (no Public/Private split), the module root `Source/ModuleName/` is the only include directory.

## 7. `MakeOutgoingSpec` vs `MakeOutgoingGameplayEffectSpec`

Two different methods on two different classes:

| Context | Method | Class |
|---------|--------|-------|
| Inside a GAS Ability | `MakeOutgoingGameplayEffectSpec(EffectClass, Level)` | `UGameplayAbility` (inherited) |
| On ASC directly | `ASC->MakeOutgoingSpec(EffectClass, Level, Context)` | `UAbilitySystemComponent` |

`MakeOutgoingGameplayEffectSpec` on the ability still works in UE 5.7 — it's a member of
`UGameplayAbility` that auto-creates a context and wraps `ASC->MakeOutgoingSpec`.

**Common mistake:** trying to call `ASC->MakeOutgoingGameplayEffectSpec(...)` from a
component or manager class (not inside an ability). That method does not exist on ASC.

`cpp
// ❌ Does NOT compile — no such method on UAbilitySystemComponent
FGameplayEffectSpecHandle Spec = ASC->MakeOutgoingGameplayEffectSpec(EffectClass, Level, Context);

// ✅ Correct — ASC's method is MakeOutgoingSpec
FGameplayEffectSpecHandle Spec = ASC->MakeOutgoingSpec(EffectClass, Level, Context);
`

## 8. `EndAbility` Overload and `SetTimerUGameplayAbility::EndAbility` has multiple overloads (your override + the base class).
Using `&UMyAbility::EndAbility` in `SetTimer` causes overload resolution failure.

**Fix:** wrap in a lambda:

`cpp
FTimerManager& TM = Avatar->GetWorld()->GetTimerManager();
TM.SetTimer(TimerHandle, FTimerDelegate::CreateLambda([this]() {
    if (IsValid(this))
        EndAbility(CurrentSpecHandle, CurrentActorInfo, CurrentActivationInfo, true, false);
}), Delay, false);
`

Common in abilities with timer-driven windup/recovery phases (attack, dash, cast).
Test `IsValid(this)` inside the lambda — the ability instance may have been GC'd.

## 9. `FActiveGameplayEffectHandle` Return Type

`ApplyGameplayEffectSpecToSelf` returns `FActiveGameplayEffectHandle`, not a spec handle.
This is the handle needed for later removal:

`cpp
FGameplayEffectSpecHandle Spec = ASC->MakeOutgoingSpec(EffectClass, Level, Context);
if (Spec.IsValid())
{
    FActiveGameplayEffectHandle ActiveHandle = ASC->ApplyGameplayEffectSpecToSelf(*Spec.Data.Get());
    // Store ActiveHandle for later: ASC->RemoveActiveGameplayEffect(ActiveHandle);
}
`

## 10. UHT: No Raw Pointers to USTRUCTs in UFUNCTION Returns

`UFUNCTION(BlueprintPure)` cannot return raw pointers to USTRUCT types:

`cpp
// ❌ UHT error: "Inappropriate '*' on variable of type 'FMyStruct'"
UFUNCTION(BlueprintPure)
FMyStruct* GetMyStruct();

// ✅ Correct: return by value or by index
UFUNCTION(BlueprintPure)
FMyStruct GetMyStruct() const;
UFUNCTION(BlueprintPure)
int32 GetMyStructIndex() const;
`

## 11. Cooldown GE Tag Workaround

Since `GrantedTags` is removed from the GE constructor, cooldown tags must be set via
`DynamicGrantedTags` at spec-application time. Two patterns:

**Manual cooldown (simpler, single-player):**
Use a timer in `EndAbility()` with `FTimerDelegate::CreateLambda` to enforce cooldown
without relying on GAS tag checks. The ability's `CommitAbility()` still works for cost
checking, but the blocking of re-activation is timer-driven.

**Full GAS cooldown (for multiplayer/tag-driven systems):**
Override `GetCooldownTags()` on the ability to return custom tags, or apply the cooldown
GE manually with `DynamicGrantedTags` set on the spec at the application point (not in
the GE constructor).

## 12. `EInputActionValueType` Enum

The `ValueType` property on `UInputAction` may have different available values in UE 5.7.
If `EInputActionValueType::Digital` or `::Axis2D` fail to compile:

`cpp
// ❌ May not compile in UE 5.7
IA_Move->ValueType = EInputActionValueType::Axis2D;

// ✅ Safe: don't set ValueType explicitly; let the IMC mapping infer it
IA_Move = CreateDefaultSubobject<UInputAction>(TEXT("IA_Move"));
// ValueType is auto-inferred from IMC mapping context triggers
`

## 13. Module Dependencies for GAS + UI + AI

Each subsystem requires specific module dependencies in `Build.cs`:

`csharp
PublicDependencyModuleNames.AddRange(new string[]
{
    "GameplayAbilities", "GameplayTags", "GameplayTasks",  // GAS
    "AIModule",                                             // AI (AIController, behavior tree)
});

PrivateDependencyModuleNames.AddRange(new string[]
{
    "EnhancedInput", "InputCore",  // Enhanced Input
    "Slate", "SlateCore", "UMG",   // UI widgets (UserWidget, HUD)
});
`

Missing any of these produces `fatal error C1083` on include or `LNK2019` on link.
`AIModule` is Public because `AController` inherits from it transitively.

## 14. Relative Include Paths in Subdirectory Modules

When organizing source into subdirectories (`Abilities/`, `Effects/`, `Rogue/`, `Rooms/`),
use `../` relative paths to reference files in sibling directories:

| In file | To include | Write |
|---------|-----------|-------|
| `Rogue/ARoguePlayerCharacter.h` | `PlayerCharacterBase.h` (root) | `#include "../PlayerCharacterBase.h"` |
| `Abilities/GA_Dash.h` | `Rogue/URogueGameplayAbility.h` | `#include "../Rogue/URogueGameplayAbility.h"` |
| `Effects/GE_DashCooldown.h` | `GameplayEffect.h` (engine) | `#include "GameplayEffect.h"` (works for engine paths) |

**Rule of thumb:** `#include "..."` first searches the source file's own directory.
For engine/plugin headers, the module dependency adds the include path automatically.
For project-internal headers in subdirectories, `../` is required.
